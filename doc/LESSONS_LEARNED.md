# 经验总结(Lessons Learned)

阅读路线:初学者先读 [IMPLEMENTATION_GUIDE.md](IMPLEMENTATION_GUIDE.md) 建立全景,再回来看本文的方法论。

本文归纳 AutoCellLibX × ASTRAN 修复过程中可复用的经验,每条都附本次的**实证**,以便判断何时适用。逐个缺陷的完整记录见 `doc/AUDIT_REPORT.md` §5;面向"下一个改代码的人"的精炼条目见 `AGENTS.md`。

## 一、方法论(可迁移到其它 EDA/数值流水线)

### 1. 必须有一个独立参照物来判断对错
本次把 CBC 的目标值与上游真实 Gurobi 的结果对比:修复后 `7.38475e6`,上游 `7.38831e6`——几乎一致,才敢确认修复正确;而修复前的 `1.71022e7` 看起来"也能跑出结果",极容易被当成正常输出。
**没有参照物,"能跑通"和"算得对"无法区分。**

### 2. "成功"标志不能掩盖失败
求解器返回 `NO_SOLUTION_FOUND` 时,适配层写了全零解,压缩被整段跳过却没有任何告警,版图悄悄变宽——数字仍然"生成成功"。
**失败要响亮**:写日志、留痕迹,最好让上游能察觉,而不是给一个空结果充当有效结果。

### 3. 被比较的一切必须共享配置
行高不一致时(基准 H=3.2 / 产物 H=2.6 / 目标库 GSCL45 H=2.47),"面积 ∝ 宽度"不成立,宽度比较无意义:实测把一个候选从 **+6.5%** 翻成 **−19.5%**。
**先对齐行高(或确认比较量与几何无关),再谈增益。**

### 4. 可复现是比较的前提
`PYTHONHASHSEED` 让导出的 `.sp` 每次都不同:既让"按网表判定版图缓存"永远失效(每次重跑都重生成全部单元),也让结果无法复现——`COMPLEX*` 的 id↔图案映射在不同运行间漂移,提交的产物因此自相矛盾。
**任何进入产物(尤其进入缓存键)的遍历顺序都必须被固定。**

### 5. 不要相信无法复现的"基准数据"
`original_astran_cells/` 由**另一套** ASTRAN(日志自证:Linux + `/opt/gurobi950` + `cellsHeight=16`)产出,本仓库造不出来。要么用 vendored 工具链重建,要么明确标注其来源与不可复现性。
**基准数据的可复现性,和它是否正确一样重要。**

### 6. 输入里的数值垃圾要按语义处理,而不是"糊"过去
ASTRAN 会成对写出同一表达式的定义约束,一条系数 `0.000000`、其孪生约束却是 `inf`。`inf` 的语义是"无界",正确做法是**丢弃该项**(退化成与孪生约束一致);夹成 big-M 1e9 等于把约束改成 `astranExpr = y + 1e9·x`,直接把模型做死。
**用大常数"兜底"一个非有限值,通常是在悄悄改变问题的含义。**

### 7. 派生数据必须随输入失效
缓存的 `.gds` 在 `.sp` 变化后仍被复用,导致"面积数字对不上它声称的网表"(网表 26 管、日志 30 管)。
**缓存键必须是真正的输入**,且"输入是否变化"的判断要可靠(本次先让写文件变成幂等,才让 mtime 可用)。

### 8. 去重判断要检查正确的键/值类型
`dumpedPaterns` 以字符串轨迹为键,却拿整型 `clusterTypeId` 去查 `.keys()`——恒为真,于是**从不去重**;后果是同一图案以两个 id 同时存在、节省量被重复计数。
**这类 bug 完全静默**,只能靠针对性测试或数据集级校验发现。

### 9. 超时/容差是在用正确性换速度,必须显式记录
"相对 gap 0.02 + 每次求解 300s 上限"能压住运行时间,但会让部分模型找不到可行解,从而静默跳过压缩。
**这类策略要可配置、可观测,并在文档中写明它对结果的影响**(本项目已写明:压缩作用于已合法版图,故只影响"压得多紧")。

### 10. 在产物被消费的层级上做验证
单测通过≠结果可信。数据集级校验(图案码唯一、日志晶体管数 == 网表 `M` 行数)离"人真正看到的东西"更近,也正是它抓住了重复与过期两类缺陷。

## 二、具体坑位(本项目专属,详见 AGENTS.md)

- ASTRAN 把**表达式**放在 LP 变量槽位 → 必须自解析 LP,不能用 CoinLpIO 回退的列名;
- 带 gap 时 CBC 返回 `FEASIBLE` 而非 `OPTIMAL` → 必须都算成功;
- 求解失败会写出**全零解** → 压缩静默失效、版图变大;
- ASTRAN 偶发 `inf` 系数 → 丢弃该项(勿 big-M);
- `COMPLEX<n>` 的 id **每次运行都会变**(且曾受 hash 顺序影响);
- 一次重跑**不会清理**旧的 `COMPLEX*`,孤儿文件会混进数据集;
- 两次 ASTRAN 不能并发(共享 cwd 下的 `ILPmodel.lp/.sol`);
- `Astran.exe` 会被 360 误报(其 `_popen`);`wx-config` 在 Git Bash 下会解析错。

## 三、这次真正起作用的调试手法

| 手法 | 作用 |
|---|---|
| 字节级 diff 新旧日志 | 发现 `COMPLEX1` 的日志写 `30` 管、而网表只有 `26` 管 → 定位"过期缓存复用" |
| 不同 `PYTHONHASHSEED` 跑同一流程、比对 md5 | 证明导出网表不确定 → 定位 hash 顺序 |
| 在生成的 LP 里搜 `inf`,并发现"孪生约束系数为 0.000000" | 证明 big-M 化改变了约束含义 → 定位求解器病态 |
| 用 git 里的历史日志 / `bestRecord-*` 交叉验证 | 发现提交的快照混用了多次运行,id↔图案对不上 |
| 从 `.lef` 的 `SIZE` 取目标库行高 | 确立比较基准(H=2.47),判定基准/产物行高都不对 |

**共同点:先找"可对照的事实"(另一份日志、另一个进程、另一份产物),再下结论。**

## 四、流程经验

- **及时提交**:把"已修好且已验证"的部分尽快 commit;长跑、易波动的产物绝不与代码混在同一提交里。
- **每个契约配一个回归测试**:缓存判定、去重、可复现性、几何常量、数据集自洽——修复投入很小,防止回归的价值很大。
- **修复与结论一起写进 `doc/AUDIT_REPORT.md`**:只存在于代码里的修复等于没记录;快照类结论(如"某次运行得到 X")必须写明其可复现条件。
- **区分"代码缺陷"与"工艺标定"**:行高对齐、层映射这类需要 DRC/工艺输入的,应记录为待标定项,而不是硬改到"看起来能跑"。
